CAN bus simulator: six sensors and a dashboard

Six sensor nodes measure a vehicle: wheel speed, engine speed, throttle, steering angle, coolant temperature and fuel level. Each one samples its sensor on a timer, packs the reading into a CAN frame and sends it over the simulated bus. A dashboard node listens, decodes every frame it receives and shows the latest value of each sensor.

A CAN frame carries no “this is fresh” flag. If frames stop arriving, the dashboard simply keeps the last number, so the only way to notice is to check how old that number is. Overload the bus or fill it with noise and you can watch the readings go stale while the real vehicle keeps moving.

Path through this page: 1) Meet the sensors and what each frame looks like. 2) Set the bus and pick when trouble starts. 3) Press Play and watch the dashboard, the chart of true against displayed values, the bus timeline and the frame log. 4) Read the whole-run table to see who lost samples and by how much. 5) Check yourself.

1. The sensors and their frames

Every sensor sends one message with its own identifier. The value is scaled to an integer (raw = (value − offset) / scale), rounded, and sent least-significant byte first, so the frame is only as precise as its scale step. A lower identifier means a higher priority. You can change how often each sensor sends.

Identifiers, scales and ranges are illustrative, and each sensor has its own node so that one node going bus-off hides one sensor. In a real vehicle several of these would share a controller, and they often sit on different buses behind a gateway. The demo drains the fuel tank far faster than a real one so that you can see it move.

2. The bus and the trouble

The run lasts 16 seconds and starts healthy. At the moment you choose, trouble begins: other ECUs start flooding the bus, noise starts corrupting frames, or both, and after a while it stops again. Try a preset, then change the sliders.

Every sensor is compared with its own period. Samples taken is how many readings the sensor sampled, and Lost counts samples that were replaced in the transmit buffer by a newer one before the bus took them. Stale is the share of the run in which the dashboard’s reading was older than the stale limit. Worst error is the largest gap between the true signal and the displayed value, checked every millisecond, as a percentage of that sensor’s chart span.

Check yourself

The wiring is fine and no node has failed, yet a tile shows a confident number. Why does it not warn me?

Because a classical CAN frame has no freshness field. The receiver sees a frame when one arrives and nothing at all when none does, so a dashboard that only remembers the last value has no way to tell. The fix is in the application: note when each frame arrived and treat a value as stale once it is older than a few periods, which is what the stale limit does here. Real systems often add an alive counter or a checksum in the data bytes so that a repeated or frozen frame can also be spotted.

Why do coolant and fuel go stale first when the extra traffic has a middle priority?

Arbitration is decided by identifier, lowest first. Extra traffic at 0x200 loses to wheel speed, steering, engine speed and throttle, so those four still get through, but it beats coolant (0x340) and fuel (0x3F0). When the bus has no room left, the lowest-priority messages are starved first. Try the highest-priority setting and every sensor goes with it.

Extra traffic of 100% at the lowest priority, yet the sensors look healthy. Is the bus not overloaded?

The bus is full, but the sensors win every arbitration, so the only cost is that a sensor frame may have to wait for the frame already on the wire to finish, because a frame in progress is never interrupted. That is at most one frame of the extra traffic, about a quarter of a millisecond at 500 kbit/s. The extra traffic is the one that suffers.

Slow sensors seem to survive bad conditions better. Is that luck?

No. Coolant temperature and fuel level change slowly, so an old value is still close to the truth, and the worst-error column stays small even when the silence is long. Wheel speed and steering angle change quickly, so the same silence leaves the dashboard far from the truth. How stale is too stale depends on how fast the quantity moves, which is why the stale limit here is a multiple of each sensor’s own period and not a fixed time.

Why does 5% noise barely matter but 30% empties the dashboard?

Each noise hit destroys a frame, which is sent again, and raises the sender’s transmit error counter by 8; every good frame lowers it by 1. At 5% the counter drifts down and the node recovers between hits, so you only see extra delay. Once more than about one frame in nine is hit, the counter climbs, the node goes error-passive at 128 and bus-off above 255, and it stays silent until it restarts. The bus only requires a minimum recovery sequence of 128 × 11 bit times (about 3 ms at 500 kbit/s), and when a node actually restarts is usually left to the controller software, so the setting “Restart after bus-off” lets you compare the minimum with longer delays. Step 2 shows the counters moving one frame at a time.

Bus load is under 100% and still readings arrive late. How?

Load is an average, and delay is caused by what is on the bus at the moment a sample becomes ready. If several sensors sample on the same tick they queue behind one another, and a frame in progress or a retransmission pushes everything back. Switch Sampling to “All on the same tick” and compare the maximum delay of the lowest-priority sensor.

A sample was replaced in the transmit buffer and never sent. Has the dashboard lost information?

Yes, one sample, but this is deliberate. Each sensor here has a single transmit buffer, so when a new reading is ready the unsent old one is dropped. If instead every sample waited in a queue, an overloaded bus would deliver old readings in order and ever later; for a sensor you almost always want the newest value. The Lost column counts these drops.
